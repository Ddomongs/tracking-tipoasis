## 1. 목표와 전제

### 운영자가 정한 것
- 목표: 구매 고객이 가장 빨리 안심하고 다음 행동을 바로 아는 통관·배송 조회 서비스.
- 읽히는 순서: 조회 → 지금 상태 → 예상일 → 해야 할 일. 상세 이력은 필요할 때만 펼칩니다.
- 문의·스토어·광고는 상태 규칙에 맞는 자리에만 둡니다.
- 운영자가 공지·스토어 링크·추천 상품·문의 경로를 한 곳에서 바꿉니다. 내부 CS 도구도 개선합니다.
- 구조와 시각 톤을 모두 대대적으로 바꿉니다(운영자 지시).
- 고객은 두 경로로 모두 들어옵니다: 주문·배송 안내의 링크(`/{번호}`)와 홈에서의 직접 입력. 둘 다 1급 입구로 설계합니다.
- 현재 조회 폼의 예시 번호는 실제 고객 화물입니다("화주는 고객입니다"). 실제 번호는 화면·테스트·문서 어디에도 두지 않습니다.

### 바꾸지 않는 것
- `POST /api/track` 요청·응답 계약(`lib/schemas.ts`)과 `lib/services/` 조회·파싱 로직, 캐시, 레이트리밋. 서버 경로 개선은 16장의 승인 항목 5로만 진행합니다(계약은 그대로).
- 클라이언트는 `/api/track`만 호출합니다. API 키는 서버 전용입니다. 조회 기록은 서버에 저장하지 않습니다.
- E2E로 잠긴 비즈니스 규칙: 오류는 문의 우선·스토어 홍보 없음, 국내 도착 전은 문의 + 구매처 선택지, 배송 중은 쇼핑 링크를 주 흐름 밖에, 배송 완료는 스토어 선두, 모바일 첫 화면에 상담·스토어 바로가기, 오래된 이력은 예상일 대신 확인 안내, 고객 언어(브랜드·로봇·AI 문구 금지), 유한 모션과 reduced-motion 존중. 규칙 문언이나 시각 위계를 바꾸는 것은 16장에서 승인받습니다.
- 조회·결과 영역의 `data-ad-exclude`와 body의 `google-anno-skip`.
- 한국어 고객 언어, WCAG 2.2 AA, 키보드 조작.
- 새 외부 서비스는 제안만 하고 승인 없이 설치하지 않습니다.

## 2. 설계 원칙

1. **한 슬롯, 한 자리.** 조회 중·오류·결과는 같은 자리(상태 카드)에서 바뀝니다. 고객의 눈이 이미 있는 곳에서 변화가 일어나야 합니다.
2. **결과 모드는 결과만.** 결과 화면 첫 화면에는 번호 바 → 상태 카드 → 도착 예상 → 지금 할 일 → 마지막 처리만 둡니다. 마케팅·스토어·광고는 그 아래, 규칙이 허락할 때만 옵니다.
3. **상태의 진실은 한 곳.** 모든 문구와 배치는 순수 함수 `deriveTrackingView`와 설정의 상태 안내 표에서 나옵니다. 고객 화면, CS 답변, 테스트, 분석 이벤트가 같은 표를 씁니다.
4. **할 일이 없으면 없다고 말한다.** 정상 대기 상태의 주인공은 "지금은 하실 일이 없어요"와 걱정 기준 날짜입니다. 문의 버튼은 문제 상태에서만 주 버튼이 됩니다.
5. **번호는 우리 밖으로 나가지 않는다.** 주소 정리가 끝나고 광고 허용 상태가 확정된 뒤에만 광고 로더를 넣습니다. 실패하면 광고를 넣지 않는 쪽으로 멈춥니다.
6. **시간이 흐르면 화면도 말한다.** 긴 대기에는 단계별 문구, 취소, 경과 시간이 있습니다. 원인이 응답으로 확인되지 않으면 원인을 단정하지 않습니다.
7. **운영자는 코드 대신 설정을 고친다.** 공지·연휴·채널·고지·추천·상태 문구는 검증되는 설정 파일 하나에 있습니다.
8. **예산은 CI가 지킨다.** JS·폰트·CSS·HTML·LCP·접근성 위반을 숫자로 잠급니다.

## 3. 전체 구조: 라우트, 화면 모드, 두 진입 경로, 주소 정리

**라우트**
- '/' 조회 화면: 정적 렌더 + revalidate 300초(공지 시작·종료 반영). searchParams를 읽지 않으므로 현재 CDN MISS 5/5(PERF-06, app/page.tsx:10-13)가 HIT로 바뀝니다. '/?trackingNumber=X'는 next.config redirects(has query)로 '/X'에 307합니다.
- '/{번호}' 결과 진입: 서버는 identifyTrackingNumber(import만)로 형식만 보고 셋으로 나눕니다.
  · 정상 형식: 결과 셸(번호 바, '조회하고 있어요' 카드)을 SSR합니다.
  · 영숫자 6~30자인데 규칙 불통과: API 호출 없이 INVALID 화면을 SSR합니다.
  · 점이 든 경로 등 나머지: 진짜 404(SEO-01 soft-404 해소).
  선택 쿼리 ?c=CJ|EPOST|HANJIN|LOTTE|LOGEN으로 택배사를 이어받습니다. 응답은 X-Robots-Tag noindex, Cache-Control private·no-store이고, 문서 제목에 번호를 넣지 않습니다.
- '/privacy'는 정적, '/internal/cs-helper'는 (internal) 그룹(광고 없음), robots.txt·sitemap.xml은 실파일.

**화면 모드** 두 라우트는 같은 서버 셸(TrackingPage, initialNumber만 다름)을 그립니다. 모드는 주소가 아니라 컴포넌트 상태로 정합니다(GAP1-10): 조회 → 조회 중 → 결과 또는 오류. [다른 번호 조회]는 라우터 이동이 아니라 상태 리셋입니다.

**두 진입** 알림 링크는 첫 페인트부터 번호와 '조회하고 있어요'가 보이고, 직접 입력은 폼이 있던 자리에서 결과 모드로 바뀝니다. 제출 순간 두 입구는 같은 화면이 됩니다.

**주소 정리: 후보 B, GAP1-02 순서**
① SSR 셸에는 광고 스크립트 0
② 하이드레이션 즉시 조회 시작
③ useEffect에서 history.state.__NA 확인(없으면 rAF 재시도, 끝까지 없으면 광고 없음)
④ sessionStorage에 {번호, 택배사, 시각} 1건
⑤ replaceState(null,'','/')(해시 포함)
⑥ pathname '/' 재확인 뒤 urlSafe
head 인라인 방식은 금지합니다(GAP1-01, RSC 135–226회).
- 복원: reload·back_forward에서만, 탭 한정 1건, 30분.
- 뒤로가기: 번호 없는 같은 주소 항목을 쌓아 조회 화면으로 돌아오게 하되, local-router 회귀 통과 전에는 만들지 않습니다.
- 공유: [다시 볼 링크 복사], 모바일은 공유 시트 우선.
- 전 경로 Referrer-Policy strict-origin.

**데스크톱 1440** 결과 왼쪽 560px에 상태·예상·할 일, 오른쪽 320px에 공지·도움말·처리 내역 '최근 3건 + 전체 보기'. 광고 레일은 왼쪽 여백만 씁니다. JS가 없으면 GET 폼 → 307 → 셸 + noscript 안내로 이어집니다.

## 4. 조회 영역: 첫 화면, 입력, 형식 안내, 바로가기 행

**첫 화면 375x812, 약 500px 안**
헤더 48px(왼쪽 '통관·배송 조회', 오른쪽 텍스트 '문의') → 공지(있을 때 한 줄, 최대 56px) → h1 '통관부터 국내 배송까지 한 번에 확인'(E2E 문언) → 입력칸 56px(레이블 '조회번호 (HBL 또는 운송장)') → 형식 안내 → 택배사(combobox '국내 택배사', 기본 '자동으로 찾기') → [조회하기] 52px → 상담·스토어 바로가기 행.
현재 입력칸 docTop 860, 조회하기 928로 첫 화면 밖이던 문제(UX-06)가 사라집니다.

**입력**
- 속성: inputmode=text, autocapitalize=characters, autocomplete=off, enterkeyhint=search. 모바일 자동 포커스는 하지 않습니다(키보드가 화면을 덮음).
- 정규화: 공백·하이픈·전각 숫자를 정리하고 영문은 대문자로 바꿉니다.
- 알림 문장을 통째로 붙여 넣으면 번호 토막과 택배사를 뽑고 '택배사를 CJ대한통운으로 맞췄어요 [되돌리기]'라고 알립니다.
- O↔0, I/l↔1이 의심되면 제출 전에 '영문 O가 섞여 있어요. 숫자 0인가요?'라고 묻습니다(3.3.3).
- 형식은 identifyTrackingNumber로 클라이언트에서 먼저 검사하고, 오류는 서버를 부르지 않고 입력칸 아래에 알립니다.

**예시 대신 형식 안내**
예시 조회 버튼은 삭제합니다(현재 두 번호는 실제 고객 화물). 누를 수 없는 한 줄만 둡니다: '숫자 10~14자리 (예: 0000 0000 0000) · 영문 3~4자로 시작하는 HBL (예: ABCD 0000 0000) · 공백·하이픈은 자동으로 빼요'.
화면, 문서, 설계 시안, CS 예시 모두 0000·ABCD·TEST 계열만 씁니다.
'번호는 어디서 찾나요?' 펼침: 네이버 주문상세 → 배송조회, 쿠팡 주문목록 → 배송조회, 톡톡 출고 안내문.

**바로가기 행**
자동 팝업(1280x720에서 조회하기 100% 가림, GAP3-01)을 없애고 조회하기 바로 아래에 비모달 region '상담·스토어 바로가기'를 둡니다.
- 확정형 쿠팡 고지 한 줄이 먼저 오고, 이어서 [톡톡 상담][네이버 스토어][쿠팡 스토어]가 44px 외곽선으로 옵니다(조회하기보다 약한 무게).
- 행 하단은 375x667에서도 550px 이하로 둬 모바일 하단 앵커와 겹치지 않게 합니다(GAP4-03).
- 조회 중·오류 동안에는 네이버·쿠팡을 숨기고 톡톡만 남깁니다.

**첫 화면 아래**
'보통 이렇게 걸려요'(4구간 소요, 설정값) → 쇼케이스 카드 2장 → 수동 광고 슬롯 → 푸터 순서입니다.
삭제하는 것: 히어로 설명, LogisticsFlow, AssuranceRail, 입력칸 흔들림 등 무한 애니메이션 5개, 헤더 스토어 링크.
데스크톱은 가운데 560px 한 열입니다.

## 5. 조회 중과 실패: 시간에 따른 표시, 원인별 안내, 포커스

**원칙**
로딩·오류·결과는 한 슬롯(상태 카드)에서 바뀝니다. 수동 조회는 폼이 있던 자리, 딥링크는 번호 바 바로 아래로, 모두 첫 화면 안입니다. 지금은 오류가 docTop 1465px에 그려지고 포커스가 BODY에 남습니다(GAP3-03).
입력은 disabled로 잠그지 않고 aria-busy만 겁니다. 새로 제출하면 AbortController로 이전 요청을 취소합니다.

**시간축**
- 0–0.4초: 버튼 라벨만 '조회 중…'.
- 0.4–3초: '조회하고 있어요' + 결과와 같은 높이의 정적 스켈레톤.
- 3초: '해외 화물은 여러 해의 기록을 찾아서 조금 더 걸려요. 보통 10초 안에 끝나요.' + [조회 취소].
- 8초: '기록이 없는 번호는 30초 가까이 걸릴 수 있어요. 번호가 맞는지 한 번 봐 주세요.'(live 1회) + 경과 '12초째'(5초 단위). 택배사를 골랐다면 '택배사 공식 조회로 먼저 보기'.
- 스피너는 5초 뒤 멈추고, 시간으로 채우는 퍼센트 막대는 쓰지 않습니다.
- 타임아웃: 항목 4 배포 전 45초, 배포 후 25초(config.lookup). 결과 없음 경로가 29.19–40.19초라(GAP2-01), 25초로 끊으면 정상 pending·NOT_FOUND가 오류로 바뀝니다.

**원인별 분기(classifyFailure)**
- INVALID(선검사·400·413·415): 입력칸 오류로 처리하고 포커스는 입력칸에 둡니다.
- NOT_FOUND: '확인 필요' 톤으로 번호 확인과 입항 전 설명을 보여 주고, 걱정 기준은 7일입니다.
- 429·503·504·비JSON 5xx·오프라인: '조회가 잠시 지연되고 있어요 · 번호 문제는 아니에요' + [다시 조회]. 429는 10초 카운트다운 뒤 버튼을 활성화하고, 오프라인은 연결이 돌아오면 1회 자동으로 다시 조회합니다.
- 클라이언트 타임아웃: 원인이 확인되지 않았으므로 '번호 문제는 아니에요'를 쓰지 않고, 번호 확인과 다시 조회를 함께 안내합니다.
- 500·계약 위반: [문의 내용 복사하고 톡톡 열기]가 주 버튼입니다.
- 2회 연속 실패: 톡톡을 주 버튼으로 올립니다.
- 서버 원문('관리자에게 문의해주세요')은 쓰지 않습니다. 5개 코드가 같은 문구로 끝나던 문제(CS-01, GAP2-05)가 이렇게 나뉩니다.

**포커스·낭독**
레이아웃에 polite live region 1개를 미리 둡니다. 결과나 오류가 정해지면 보이는 상태 제목(h2, tabindex=-1)으로 포커스를 옮깁니다. 딥링크는 고객이 다른 곳을 조작하지 않았을 때만 옮깁니다.
role=alert는 오류 문장에만 붙이고, 포커스를 받는 제목에는 붙이지 않습니다(이중 낭독 방지).

**서버, 승인 시**
목표는 결과 없음 응답이 L=0.3초에서 3초 이하, L=1.5초에서 6초 이하이고, 장애는 15초 안에 API_TIMEOUT으로 응답하는 것입니다. 클라이언트 쪽 변경은 승인과 무관하게 먼저 출시합니다.

## 6. 결과 영역: 요약 → 다음 행동 → 상세, 상태 신호

**순서 고정**
결과 첫 화면은 번호 바 → 상태 카드 → 도착 예상 → 지금 할 일(CTA 블록) → 마지막 처리 순서입니다.
- 이 사이에는 광고·스토어·추천·배너를 넣지 않고, 상태 관련 공지는 카드 안 '안내' 한 줄로 넣습니다.
- 제목 구조: 시각적으로 숨긴 h1 '배송 조회 결과' + 상태 제목 h2.

**번호 바**
4자리씩 묶은 고정폭 숫자로 쓰고 말줄임은 0입니다. 320px에서는 [번호 변경][다시 조회]가 다음 줄로 넘어갑니다.

**상태 카드와 상태 신호**
- 칩(예: '통관 대기 · 2/4'), h2 고객 문장, 이유 한 줄.
- 진행 표시는 4구간 가로 미니 척추 하나로 통일합니다(지금은 진행 모델 4개가 겹침, DES-03): <ol aria-label='배송 여정 4구간'>에 aria-current=step 정확히 1개.
  · 구간: ①해외 출발 ②입항·통관 ③국내 배송 ④도착.
  · 코드 1–3과 코드 4(통관 완료·인계 대기)는 ②, 코드 5–6은 ③, 코드 7은 ④.
  · pending·NOT_FOUND는 '위치 확인 전'으로 표식을 달지 않습니다.
- 문제 표식은 색·아이콘·텍스트를 함께 씁니다: 멈춤(stale), 끊김(택배사 조회 지연), 갈림(여러 택배사).
- 톤 5종: 정상 진행, 정보 대기, 확인 필요, 문제, 완료.

**도착 예상**
화면에서 가장 큰 글자(32–40px)와 D-n으로 보여 줍니다.
- 연휴가 계산 구간과 겹치면 '추석 연휴 영향 · 1~2일 늦어질 수 있어요' 배지를 달고 D-표기와 '오늘 예상'을 숨깁니다.
- stale은 '지금은 도착 예상일을 안내하기 어려워요', pending은 '정보 등록 후 안내'로 씁니다.

**지금 할 일**
문장 1개, 주 행동 최대 1개, 보조 1–2개로 구성합니다.
- 정상 대기에서는 '지금은 하실 일이 없어요'가 주인공이고 채움색 버튼이 없습니다.
- 걱정 기준 날짜('9월 29일(화)까지 그대로면 알려 주세요')를 톡톡 텍스트 링크에 묶습니다. 현재 이런 기준 문구가 있는 상태는 0/7입니다(CS-02).

**overdue**
오늘(KST)이 걱정 기준일을 넘으면 같은 상태가 '확인 필요' 톤으로 바뀝니다. [문의 내용 복사하고 톡톡 열기]가 주 버튼이 되고, 추천·광고는 0입니다.

**상세**
마지막 처리 한 줄('9월 23일 (수) 14:10 · 통관 접수', 원어는 작게) 아래에 <details> '처리 내역 11건 보기'를 둡니다. 지나온 구간의 세로 척추와 구간별 기록은 이 안에 넣습니다.

**결과 도착 시**
스켈레톤 자리를 채우므로 스크롤 점프가 없습니다(현재 1,295px). live region이 한 문장을 읽고, 문서 제목은 '통관 대기 중 · 배송 조회'가 됩니다.

#### idle — 홈('/') 조회 전

#### error · INVALID_NUMBER(형식 오류: 클라이언트 선검사·서버 400/413/415·형식이 틀린 딥링크)

- 보조: '번호는 어디서 찾나요?'(이 상태에서는 기본으로 펼침), 톡톡(블록 첫 링크)
- 접힘·숨김: 바로가기 행의 네이버·쿠팡 숨김(톡톡만 남김), 쇼케이스·추천·광고 슬롯 숨김, 서버 원문 메시지 비노출

**광고**
- 로더 조건: 주소에 번호가 없고, 광고 허용 상태가 확정됐고, /internal이 아닐 때. 딥링크 첫 결과가 문제 상태면 보류했다가 같은 탭에서 허용 결과가 나오면 1회 삽입합니다.
- 홈: 조회 전에 로더가 들어가면 오류 화면에 하단 앵커가 남습니다. 그래서 첫 결과가 허용 상태로 확정되거나 고객이 쇼케이스까지 스크롤한 뒤에 삽입합니다(승인 항목).
- 자동 광고는 모바일 하단 앵커와 데스크톱 왼쪽 레일만 씁니다. in-page 자동 광고, 데스크톱 앵커, 비네트 추가 트리거는 끕니다(data-ad-exclude는 실효 없음, GAP4-01).
- 수동 슬롯은 페이지당 1개, 푸터 바로 앞에 두고 min-height를 예약합니다(모바일 280px, 데스크톱 250px). 앵커 높이만큼 scroll-padding-bottom을 둡니다(GAP4-07).
- '문제 상태 광고 0'의 정의는 수동 슬롯 0 + 신규 로더 0입니다.
- data-ad-exclude와 body의 google-anno-skip은 유지합니다.

**문의**
- 헤더 '문의'(텍스트)는 모든 화면 같은 자리에 둡니다(3.2.6).
- 톡톡은 화면당 최대 3곳(헤더, 상태별 1곳, 푸터), 스타일 1종, 라벨 2종('톡톡 상담', '톡톡으로 확인 요청')입니다. 현재는 4곳·이름 3종·스타일 6계열입니다(GAP3-13).

**스토어·제휴**
AffiliateLinkGroup이 블록 첫 요소로 확정형 고지를 자동으로 붙입니다. isAffiliate 하나가 rel=sponsored nofollow와 고지를 함께 정합니다. 현재 링크 앞에 고지가 있는 곳은 0/4입니다(CS-05).

**추천**
- 인라인 목록만 쓰고 다이얼로그는 없습니다.
- 유효기간 안의 상품만 보여 주고, 0개면 블록을 그리지 않습니다.
- '이번 주' 라벨은 유효기간이 7일 이하일 때만 씁니다.
- 가격은 상품 상세 링크와 7일 이내 확인일이 모두 있을 때만 표시합니다.

## 9. 운영 설정·공지·연휴

**한 파일, 빌드 때 검증**
- config/site.config.ts: 운영 값(한국어 주석).
- lib/config/schema.ts: zod 스키마와 superRefine 불변식. 오류는 한국어로 씁니다(예: 'notices[0].endsAt: 종료 시각이 시작보다 빠릅니다').
- parse는 서버 전용 모듈에서 하고 클라이언트에는 검증된 순수 객체만 넘깁니다. CS 템플릿은 internal 전용 파일로 둡니다.

**섹션**
1) channels: 톡톡(라벨 '톡톡 상담'), 네이버(isAffiliate false), 쿠팡(isAffiliate true), 배치별 링크, 허용 호스트(https만).
2) disclosures: 확정형 쿠팡 고지(최종 문언은 법무 확인).
3) calendar: Asia/Seoul, 공휴일(2026 추석 9/24~26, 개천절 대체공휴일, 한글날, 2027 목록), 택배 토요일 배송 여부.
4) durations: 단계별 소요 범위, 걱정 기준, pending 재확인 문구, lookup.stageMs [3000, 8000], timeoutMs 45000(항목 4 뒤 25000).
5) stateGuide: Record<GuideKey, GuideRow> satisfies. 열: tone, title, reason, nextAction, worry, primaryAction, inquiryLevel, revenueTier, etaMode. 토큰은 {etaDate} {worryDate} {lastEventDate} {carrier} {staleDays}만 허용합니다.
6) glossary: 수입신고수리 → 통관 완료, 통관목록접수 → 통관 접수, 간선하차 → 지역 터미널 도착 등(DES-07).
7) featuredProducts: 상품 상세 https 링크, validFrom·validUntil, priceCheckedAt.

**불변식**
- 문제 상태는 스토어·광고·추천 0, inTransit은 스토어 0, delivered는 스토어 선두, pending은 문의+구매처.
- 제휴 배치에는 고지가 필수입니다.
- 모든 문구에 10자리 이상 숫자, HBL 패턴, 'AI·인공지능·로봇·봇'이 있으면 실패합니다.
- staleDays는 서버 값 14일과 같아야 합니다.
설정을 바꿔도 E2E 잠금 규칙은 깨지지 않습니다.

**공지**
- kind 우선순위는 outage > delay > holiday > info이고, 제목은 20자, 본문은 80자 이하, 기간은 KST입니다. 한 화면에 1개만 보입니다.
- 위치: 홈은 헤더 아래 한 줄, 결과는 상태가 맞으면 카드 안 '안내' 한 줄, 로딩·일시 지연에는 outage만, CS 답변 끝에는 자동 첨부.
- 페이지 로드 때 낭독하지 않습니다.
- '/'는 마운트 뒤 KST로 다시 걸러, 캐시가 늦어도 끝난 공지가 보이지 않게 합니다.

**연휴**
기본은 배지 + D-표기 억제 + 영업일 걱정 기준입니다. 예: 통관 완료가 9/23(수)이면 인계 걱정 기준은 9/29(화)입니다. 빌드는 향후 60일의 공휴일 누락을 경고합니다.

**운영 흐름**
GitHub 웹 편집 → PR → CI → main → Vercel 자동 배포 순서입니다. 설·추석·택배 없는 날·UNI-PASS 점검 공지를 미리 넣어 두면 시각에 맞춰 켜지고 꺼집니다. 무배포 저장소(Edge Config)는 제안으로만 둡니다.

## 10. 내부 CS 도구

**격리**

**탭 4개(tablist·tab·aria-selected)**
① 배송 안내

② 통관부호 불일치

③ 안내표 미리보기: 모든 상태를 가짜 번호(0000 0000 0001, TEST 0000 0001)로 보여 주고 고객 화면과 CS 답변을 나란히 둡니다. 설정을 고친 뒤 배포 전에 확인하는 화면이고, 스크린샷·axe 회귀에도 씁니다.

## 11. 측정: 개인정보를 지키는 분석(제안)

**원칙**
조회번호, 전화번호, 자유 입력, IP·UA 원문, 쿠키는 어떤 경로로도 모으지 않습니다. 경로는 템플릿으로 바꾸고, 이벤트 속성은 enum만 씁니다. 2·3단계는 제안이며 승인이 필요합니다.

**1단계: 지금, 코드 변경 0**
- Vercel Observability 라우트별 요청 수를 주간으로 기록합니다: '/', '/[trackingNumber]', '/api/track' 상태 코드(200·400·404·429·5xx). 개편 전 최소 2주를 기준선으로 둡니다.

- 톡톡 문의를 주간 수기로 분류합니다: 위치·언제 와요, 통관 지연·정체, 번호·조회 안 됨, 미수령, 개인통관고유부호, 기타. '조회 화면을 보고도 문의했는지'도 표시합니다.

- 스토어는 배치별 링크 ID로 파트너 대시보드에서 배치별 클릭을 나눠 봅니다.

**2단계: 항목 4 승인 시**
번호 없는 구조화 서버 로그 {route, elapsedBucket, unipassOk, unipassFail, resultKind, errorCode}와 실패율 경보를 둡니다. UNI-PASS 장애가 NOT_FOUND로 위장되는 문제(GAP2-03)를 일찍 잡고, InsForge 폐기 판단 근거로도 씁니다.

**3단계: 방침 개정 뒤**

- 주소 정리 뒤에만 로드합니다.

- 세션 리플레이, 히트맵, 입력 캡처는 금지합니다. GA4는 권하지 않습니다.

**KPI**
1. 주간 톡톡 문의 ÷ 주간 조회 수(개편 전후 4주)
2. 정상 대기 3상태의 톡톡 클릭률(가설: 절반 감소)
3. 문제 상태 톡톡 중 문의 내용 복사 비율(50% 이상)

7. 필드 LCP·INP·CLS p75

## 13. 시각 방향과 화면 스타일

운영자 지시대로 시각 톤도 대대적으로 바꿉니다. 3단계에서 아래 공통 규칙 위에 서로 다른 세 방향을 시안으로 만들었고, 운영자는 고객이 스타일을 고를 수 있게 하되 기본값은 추천안으로 하기로 정했습니다.

### 모든 스타일이 지키는 것(의미 규칙)
- **버리는 것:** 다크 네온 인상을 만드는 글로우 그림자, 흐림 원형 장식(blob), 격자 배경, 그라디언트 버튼, 장식용 번호(01/02/03), Sparkles·DB 같은 의미 없는 아이콘(DES-08). 밝은 바탕을 강제하지는 않습니다.
- **상태 톤 5종:** 정상 진행, 정보 대기, 확인 필요, 문제, 완료. 색·아이콘·문구를 함께 써서 색만으로 구분하지 않습니다(1.4.1). 대비 검증을 통과한 값만 씁니다.
- **가장 큰 글자는 도착 예상 날짜**(32–40px, 고정폭 숫자). 마케팅 제목이 상태나 날짜보다 커지지 않습니다.
- **번호 표기:** 4자리씩 묶은 고정폭 숫자, 말줄임 없음.
- **타입 스케일 5단계**(예: 12/14/16/20/32–40px). 행동 문구 14px 이상, 11px 이하 글자 없음.
- **4구간 여정 표시(①해외 출발 ②입항·통관 ③국내 배송 ④도착)를 공통 시그니처로** 씁니다. 현재 구간 표식은 정확히 하나이고, 멈춤·끊김·갈림은 색+아이콘+텍스트로 표시합니다.
- **버튼 계층:** 채움색 주 버튼은 화면당 1개. 톡톡·스토어는 보조(외곽선 또는 텍스트)이고 문제 상태에서만 톡톡이 주 버튼이 됩니다.
- **모션:** 150–300ms 페이드·높이 변화 1회. 무한 반복 0, reduced-motion이면 0.
- **폰트 예산:** preload 2파일 이하, 첫 화면 폰트 100KB 이하. 본문은 시스템 한글 폰트 스택을 우선 검토하고, 개성을 주는 서체는 숫자·제목에 서브셋으로만 씁니다.

### 화면 스타일 선택
- **선택지:** 기본(B) · 서류형(A) · 어두운 화면(C). 푸터 바로 위 "화면 스타일" 묶음(fieldset + legend, 라디오 3개, 각 44px)에 둡니다. 헤더는 "문의"만 고정으로 두는 원칙을 지킵니다.
- **첫 방문 기본값:** 저장된 선택이 있으면 그것, 없으면 기본(B). 단, 기기가 어두운 모드(`prefers-color-scheme: dark`)이면 어두운 화면(C)으로 시작합니다. 이 규칙은 설정 `style.followSystemDark`(기본 true)로 끌 수 있습니다.
- **저장:** `localStorage` 한 값(`tt:style` = `signal` | `manifest` | `night`). 개인정보가 아니고 서버로 보내지 않습니다. 저장소가 막히면(사생활 보호 창 등) 기본값으로 동작합니다(try/catch).
- **깜빡임 방지:** `<head>` 맨 앞의 작은 인라인 스크립트가 첫 페인트 전에 `html[data-style]`을 정합니다. "/"의 정적 렌더는 유지합니다. CSP를 강제할 때는 이 스크립트를 해시로 허용합니다(`unsafe-inline` 없이).
- **구현 경계:** 스타일 = 토큰 세트(CSS 변수, `[data-style]` 범위) + 변형 슬롯 4개(상태 머리: 색면/도장/램프, 도착 예상 표기: 대형 숫자/기입값/숫자 타일, 여정 그림: 막대/운송장 경로/노선도, 버튼 모서리·채움). 컴포넌트 구조, DOM 순서, `data-*` 훅, 문구, 배치 규칙은 스타일과 무관합니다. E2E 비즈니스 규칙 테스트는 스타일에 의존하지 않습니다.
- **폰트:** 기본 스타일은 시스템 고딕 + 숫자 서브셋 1파일로 예산(preload 2파일, 첫 화면 100KB)을 지킵니다. 서류형·어두운 화면의 서체는 그 스타일을 고른 경우에만 내려받습니다(`@font-face`를 해당 스타일 범위에서만 사용).
- **접근성:** 스타일마다 대비 검증을 통과한 토큰만 씁니다. 바꾸면 live region이 "화면 스타일을 서류형으로 바꿨어요"를 한 번 읽습니다. 모션 규칙은 공통입니다.
- **품질 비용:** 시각 회귀 매트릭스는 핵심 8상태 × 2폭 × 3스타일 = 48장, axe·대비 테스트도 스타일별로 반복합니다. 화면 작업량은 단일 스타일보다 약 30–40% 늘어날 것으로 봅니다.
- **정리 기준:** 분석 도입(승인 13) 뒤 스타일 선택을 enum 이벤트로 집계하고, 거의 쓰이지 않는 스타일은 운영자와 정리를 검토합니다.

## 17. 운영자에게 확인할 것

답이 없으면 기본값으로 진행하고, 개편 뒤 문의 분류로 조정합니다.

1. **단계별 실제 소요와 '걱정 기준'을 알려 주세요. HBL은 해외 출고 후 며칠부터 조회되나요? 통관·택배사 인계·국내 배송은 보통 며칠인가요? NOT_FOUND와 pending은 며칠이 지나면 문의해야 하나요? 택배는 토요일에도 배송하나요? pending의 '2~3시간 뒤 다시 확인'은 맞는 안내인가요?**
   - 왜 필요한가: 모든 화면의 '언제까지 그대로면 알려 주세요' 날짜, overdue 전환 시점, CS 답변이 이 값으로 계산됩니다. 너무 이르면 문의가 늘고, 너무 늦으면 정체 발견이 늦어집니다.
   - 답이 없을 때 기본값: 현재 코드 상수를 씁니다(통관 1~2일, 인계 0~1영업일, 국내 1~2일). HBL 조회는 출고 후 3~7일, 걱정 기준은 예상일 +1영업일, NOT_FOUND 7일, pending 10일, 미수령 24시간, 토요일 배송은 없는 것으로 계산하고, pending 문구는 현행을 유지합니다. 4주마다 문의 분류로 조정합니다.
2. **주문·배송 알림 메시지와 톡톡 답변에 tracking.tipoasis.com/{번호} 링크가 실제로 들어가나요? 템플릿 원문을 공유해 주실 수 있나요?**
   - 왜 필요한가: 딥링크 비중(GAP3-09 미검증)에 따라 SSR 셸 최적화, 하이드레이션 전 조회 선시작, 후보 B의 수익 효과가 달라집니다.
   - 답이 없을 때 기본값: 두 입구를 모두 1급으로 설계합니다. Observability 2주 기준선에서 '/[번호]' 비중이 30% 미만이면 선시작은 보류하고, CS 도구 답변에 링크를 자동으로 넣는 일부터 합니다.
3. **공지와 추천 상품은 얼마나 자주 바뀌고, 누가 고치나요? 운영자가 GitHub 웹 편집기로 설정 파일을 직접 고치는 방식이 괜찮은가요?**
   - 왜 필요한가: 코드 설정 + PR 배포(수 분)로 충분한지, 무배포 저장소(Edge Config, 인프라 추가)가 필요한지가 이 답으로 정해집니다.
   - 답이 없을 때 기본값: 월 1~2회 변경으로 가정합니다. 코드 설정과 PR 배포로 운영하고, 설·추석·택배 없는 날 공지 템플릿을 미리 넣어 둡니다. 추천은 유효기간을 필수로 하고, 만료되면 자동으로 숨깁니다. Edge Config는 도입하지 않습니다.
4. **테스트에 남은 출처 미확인 12자리 번호(5206…0641, 3059…8213, 3059…5223, 4593…7824~28)도 실제 고객 화물인가요? 공개 저장소의 git 이력은 재작성(강제 push)할까요?**
   - 왜 필요한가: 실제 번호라면 공개 저장소에서 계속 노출됩니다. 이력 재작성은 되돌리기 어렵고, 협업·배포 이력에 영향을 줍니다.
   - 답이 없을 때 기본값: 모두 실제 번호로 간주해 작업 트리에서 가짜 픽스처로 교체하고, 일반 규칙 가드를 둡니다. 이력 재작성은 하지 않고 저장소 공개 여부 재검토를 권합니다.
5. **수익 하락을 어디까지 허용할 수 있나요? 자동 팝업 폐지, 문제 상태 광고 보류, 홈 로더 지연 삽입, 비네트 추가 트리거 해제는 모두 광고·스토어 노출을 줄입니다.**
   - 왜 필요한가: 안심 우선 설계는 수익 점수가 가장 낮고(평균 3.2), 광고는 Phase 1에서 한 번도 실제로 렌더링하지 않아 영향 추정치가 없습니다.
   - 답이 없을 때 기본값: 안심 우선 규칙을 유지합니다. 형식별 RPM과 스토어 클릭을 배포 전후 2주씩 비교하고, '/' RPM이 15% 이상 떨어지면 홈 로더 지연 규칙부터 되돌려 다시 검토합니다.

## 18. 리뉴얼에서 유지할 것

- 결과 요약 카드의 세 요소(상태명과 한 줄 설명, "지금은 이렇게 해주세요", 도착 예상 패널)와 큰 날짜·D-n 배지. 새 상태 카드가 이 구성을 이어받습니다.
- 장기 정체·국내 도착 전에 예상일을 비우고 확인 안내로 바꾸는 처리(E2E 규칙).
- 조회 성공 시 결과 제목으로 포커스를 옮기는 동작. 오류·로딩에도 넓힙니다.
- 상태별 안내 콘텐츠 규칙(오류 → 톡톡, 도착 전 → 문의 + 구매처, 완료 → 스토어 선두)과 E2E 50개의 비즈니스 규칙.
- 데이터 계약(TrackResponseData, lib/schemas.ts)과 서버 테스트, lib/delivery-carriers.ts, proxy.ts 기본 인증.
- 접근성 기반(skip link, 44px 안팎 터치 타깃, 320px 리플로우, 폼 레이블)과 reduced-motion 준수.
- 외부 링크 rel 정책(noopener noreferrer, 쿠팡 sponsored nofollow), body의 google-anno-skip, 단일 TALK_URL.
- /privacy의 정적 렌더와 올바른 canonical, 한글 줄바꿈(break-keep).
